#### 004 — Created the domain layer (batch)
- **Files:** `src/domain/types.ts`, `src/domain/schema.ts`, `src/domain/ids.ts`, `src/domain/units.ts`, `src/domain/defaults.ts`.
- **Action:** Defined the serialisable shapes the whole app shares (components, connections, workload, project), the Zod schemas that validate anything crossing a trust boundary, id helpers, unit formatters, and the default settings plus three starter templates.
- **Decisions:**
  - Components are a discriminated union on `kind`, so TypeScript narrows settings automatically and Zod can use `discriminatedUnion`.
  - A server **resource profile means hardware only** (`cpuSlots`, `ramMb`, `baselineMemoryMb`). It deliberately does not touch `cpuMsPerRequest`, `concurrencyLimit` or `memoryPerRequestMb`, because those describe the application, not the machine. This is what keeps acceptance check 5 honest: changing RAM cannot change CPU work.
  - `memoryPerQueuedRequestMb` is an explicit, editable setting rather than a hidden fraction, because the specification requires the queued-memory assumption to be visible.
  - Message sizes live on the component that defines them (`queryRequestBytes`/`queryResultBytes` on the database, `lookupRequestBytes`/`lookupResultBytes`/`populateBytes` on the cache), so transfer accounting has one source of truth.
  - Time inside the engine is milliseconds as a plain number; bandwidth is megabits per second. `transmissionMs()` in `units.ts` is the single conversion.
- **Alternatives:** Storing settings as a loose `Record<string, number>` would have made the inspector generic but removed all type safety and made validation ad hoc. A single flat `Component` type with optional fields was rejected for the same reason.
- **Bug found:** Writing `src/domain/defaults.ts` through a shell heredoc failed with an unterminated-quote error and produced no file. Rewrote it with the file-writing tool instead; larger TypeScript sources are now written that way.
- **Verification:** Not type-checked yet — no compiler run until the simulation layer exists.

#### 005 — Created the simulation primitives (batch)
- **Files:** `src/simulation/rng.ts`, `src/simulation/event-queue.ts`, `src/simulation/ring-queue.ts`, `src/simulation/metrics.ts`, `src/simulation/routing.ts`.
- **Action:**
  - `rng.ts`: mulberry32 generator plus a `RandomStreams` factory that derives an independent generator per named stream (FNV-1a hash of the name mixed with the run seed).
  - `event-queue.ts`: binary min-heap ordered by `(time, seq)`.
  - `ring-queue.ts`: circular-buffer FIFO with O(1) push/shift.
  - `metrics.ts`: `StreamingStat`, `BoundedHistogram` (exponential buckets, 0.1 ms base, ratio 1.15, 120 buckets) and `TimeWeightedAccumulator`.
  - `routing.ts`: graph construction (id map + both adjacency lists), breadth-first reachability, and the validation/route-resolution pass.
- **Decisions:**
  - Events are ordered by timestamp then by an increasing sequence number. Without the tiebreaker, two events at the same simulated millisecond could be processed in either order and results would stop being reproducible.
  - Per-stream randomness (rather than one global generator) means adding a component cannot shift the draws another component sees.
  - The latency histogram uses equal *relative* bucket widths, so the reported p95 precision can be stated as a single percentage (+/-15%).
  - Utilisation and queue length are integrated as area under a step function, which is what "time-weighted" means; sampling would bias short spikes.
- **Alternatives:** Sorting the pending-event array after every insert is O(n log n) per event instead of O(log n). `Array.shift()` for queues is O(n) per dequeue and would degrade badly under load, which is exactly the case Aparecium is built to show. Keeping every latency sample would give an exact p95 but unbounded memory.
- **Verification:** Not tested yet; unit tests follow.

#### 006 — Created the simulation models and the engine
- **Files:** `src/simulation/models/link.ts`, `src/simulation/models/station.ts`, `src/simulation/models/server.ts`, `src/simulation/types.ts`, `src/simulation/engine.ts`.
- **Action:** Implemented the discrete-event engine and the three component models it drives.
- **Key modelling decisions:**
  - **Two channels per connection.** Every drawn edge becomes a forward and a reverse `LinkChannel`, because a request going out and a response coming back do not share a queue.
  - **CPU is taken and given back in segments.** Total CPU work per request is divided evenly across the compute segments between downstream calls (`segments = downstreamCalls + 1`). The total CPU cost per request is therefore unchanged by how many calls it makes, but the CPU slot is genuinely released while the request waits on a database or cache. This is what makes acceptance checks 4 and 5 mean something.
  - **Cache hit/miss is sampled once, at request creation,** from a stream dedicated to that cache. Because the hit probability is a fixed constant, sampling at creation is distributionally identical to sampling at lookup time, and it lets the engine know up front how many compute segments the request needs.
  - **Three separate server resources:** CPU slots, application concurrency and a memory budget in megabytes. Memory is a number, never a real allocation.
  - **Measurement interval is `max(last event time, arrival window)`.** Using only the last event time would report a trickle of traffic as a high rate; using only the window would ignore work finished during the drain.
  - Cache misses return a short negative reply modelled at lookup-key size; cache write acknowledgements are modelled the same way. Both are stated in the run's assumptions list.
- **Alternatives:** Sampling the cache outcome at lookup time was the first idea; it was rejected because the number of CPU segments would then be unknown when the first segment starts. Making cache population non-blocking was considered; blocking was chosen because it is the common implementation and needs no extra bookkeeping, and it is listed as an assumption.
- **Bugs found and fixed:**
  1. `tsc` reported `stationRequest` was never used. That was a real defect, not dead code: `onDeliver` had no branches for `cacheLookup`, `dbQuery` or `cachePopulate`, so downstream messages arrived at the database and cache and were silently dropped. Added the three delivery branches.
  2. `compileRoutes(doc)` took a parameter it never read; removed it.
- **Verification:** `npx tsc --noEmit` passes with no errors.
- **Related files:** `src/simulation/routing.ts` (route resolution consumed by the engine).

#### 010 — Created the catalogs, pricing engine and storage layer (batch)
- **Files:** `public/catalogs/cloud-profiles.v1.json`, `public/catalogs/hardware.v1.json`, `src/catalogs/types.ts`, `src/catalogs/loader.ts`, `src/pricing/pricing.ts`, `src/storage/db.ts`, `src/storage/exchange.ts`, `src/storage/runs.ts`. Also modified `src/domain/types.ts`, `src/domain/schema.ts`, `src/domain/defaults.ts`, `src/simulation/types.ts`, `src/simulation/engine.ts` and `tests/helpers.ts`.
- **Decisions:**
  - **Charges are a map, not a flat list of numbers.** A charge that is absent from a profile does not apply at all; a charge present with `amount: null` applies but has no known rate. Neither is ever treated as zero. This is what makes "unpriced" a real state rather than a display trick.
  - **Rates are decimal strings in JSON and `Decimal` in code.** `0.10 x 730` is `73.00` exactly; in binary floating point it is `73.00000000000001`.
  - **Monthly projection scales a measured rate, not a run total.** Outbound bytes are divided by the run's measured seconds to get bytes per second, then multiplied by 2,628,000 seconds. A test asserts that doubling the run duration at the same traffic rate produces an identical monthly number.
  - **Rate editing lives in the document** as `pricingOverrides`, keyed by profile id, so an edit applies to every component using that profile and travels with export, import and run snapshots.
  - **Per-node egress attribution** was added to the engine's usage ledger (`egressByNodeId`) so a cost line can be attached to the component that actually sent the bytes.
  - **A run keeps a deep copy** of the document and of the catalog rows it used (`src/storage/runs.ts`). Without that, editing the canvas would rewrite history.
  - **Deleting a project deletes its runs in one IndexedDB transaction**, so it cannot half-succeed.
- **Verification:** `npx tsc --noEmit` passes. `npx vitest run tests/pricing.test.ts` — 13 passed. `npx vitest run tests/persistence.test.ts` — 11 passed. These cover acceptance checks 10, 11, 12, 13 and 14.

#### 011 — Created the Web Worker and its client
- **Files:** `src/workers/protocol.ts`, `src/workers/simulation.worker.ts`, `src/workers/client.ts`.
- **Action:** The worker drives the engine in time-boxed chunks (12 ms of work, then `setTimeout(0)`), reports progress at most every 120 ms, and answers a cancel message by stopping the engine and returning the partial result.
- **Decision:** Yielding with `setTimeout` rather than a microtask is the point of the design: a worker is single-threaded, and only a macrotask boundary lets a queued `cancel` message be delivered. Progress is time-throttled rather than per-event so a large run does not post a million messages.
- **Bug found while writing `client.ts`:** cancellation behaved differently on the worker path and the inline fallback path. On the worker path the promise resolved with a cancelled result; on the inline path `cancel()` rejected the promise *and* the loop then tried to resolve it, so the outcome depended on ordering. Fixed by tracking `activeInline` and letting the inline loop settle its own promise. A second defect in the same code was that superseding a run left its handler in the map forever, so its promise never settled; `onMessage` now settles by `runId` and only clears the active slot when the ids match.
- **Verification:** Type checking passes. Cancellation is exercised end to end by the Playwright test added later.

#### 019 — Four defects found while checking the redesign in a browser
1. **Palette crash.** Removing the category grouping left a reference to the deleted `categories` variable. The console showed `ReferenceError: categories is not defined` and React unmounted the whole tree. Found only because the console was read, and fixed by finishing the rewrite.
2. **Components hidden under the side panel.** React Flow's `fitView` centres the diagram in its whole container, but the side panel sits on top of the container's right-hand side, so the database was underneath it on first load. Added `FitToVisibleArea` in `src/features/editor/Canvas.tsx`, which frames the diagram in the uncovered band instead.
3. **`useNodesInitialized()` was permanently false,** so the first version of that fix never ran at all. The cause was in my own code: `onNodesChange` filters to `position` changes and drops everything else, including React Flow's `dimensions` changes, so a controlled flow never records that its nodes have been measured. Rather than introduce a second source of truth for node state, the framing maths now works from the document plus a fixed `NODE_WIDTH`/`NODE_HEIGHT` pair declared once and used both for the CSS box and the arithmetic, so the two cannot drift.
4. **`setViewport` was silently doing nothing.** With the effect confirmed to be running and computing correct numbers, the DOM transform stayed at the identity. The cause was the `{ duration: 220 }` option: a transitioned `setViewport` is dropped while React Flow is still building its pan/zoom instance, which is exactly when this first fires. #### 042 — Dragging a component restarted the traffic on every connection
- **Report:** "I just dragged cache from one point to another, and the simulation restarts, as you can see the dots begin to flow again. It shouldn't happen. Here the cache is not even connected… for anything, simulation should continue."
- **Files changed:** `src/features/editor/Canvas.tsx`. **Created:** `e2e/canvas-regressions.spec.ts`.
- **What was actually happening.** Not a re-run. A Playwright probe stamped an attribute on every packet circle, dragged the unconnected cache, and read back: `runId` and the offered rate were identical, so `simulationSignature` had done its job and nothing had been simulated again — but every stamp was gone, meaning the circles were new DOM elements. SMIL animations live and die with their element, so three new circles per connection meant three animations starting from zero. It looked exactly like a restart and was nothing of the kind.
- **The cause, two levels down.** `nodes` and `edges` are `useMemo` projections of the document, so every edit hands React Flow brand new node objects. `adoptUserNodes` in `@xyflow/system` keeps a node's measured handle positions only when the node it is given carries a `measured` size; without one it treats the node as re-initialised and drops them. `getEdgePosition` then cannot place the edge and returns `null`, and `EdgeWrapper` has `if (sourceX === null) return null` — so every connection was unmounted for a frame and remounted the next. A second, unrelated mutation with no pointer involved at all (`mutate` moving a node by 40px) reproduced it exactly, which is what ruled out the drag gesture itself.
- **The fix.** The node cards are a fixed size that the framing maths and the CSS already share, so the nodes now declare `measured: { width: NODE_WIDTH, height: nodeHeight }`. The handle positions survive, the connections are never torn down, and the dots keep going. If the constants ever drift from the real card size, React Flow's resize observer sees the difference and re-measures.
- **A claim I had to withdraw.** I also moved the packets from `path={path}` to `<mpath href="#edgeId">` and wrote in the comment that rewriting the `path` attribute restarts the motion. Measuring it said otherwise: with the remount fixed, phases across a drag went `[0.14, 0.80, 0.47] → [0.29, 0.96, 0.62]` on both spellings — Chrome carries on smoothly. The comment now says what is true: SMIL leaves the effect of rewriting a running animation's attributes to the implementation, `mpath` does not depend on it, and a drag no longer touches the animation elements. Kept for that reason, not for the one I first gave it.

#### 045 — Work that outlives its request, and traffic that is not flat
- **Request:** "what components are missing from the project and should be there, to make it more realistic." Chosen from the options offered: the message queue with an asynchronous consumer, plus bursty arrivals and closed-loop clients.
- **Files created:** `src/simulation/models/queue.ts`, `tests/queue.test.ts`, `tests/arrivals.test.ts`, `e2e/async-queue.spec.ts`.
- **Files changed:** the domain (`types`, `defaults`, `schema`), the engine (`engine`, `routing`, `types`, `models/station`, `models/link`), pricing (`pricing`, `catalogs/types`, the catalog JSON), storage (`run-schema`, `runs`), and the editor and results UI.

**The consumer is an Application Server, not a new "Worker" kind.** A background worker *is* an application server that takes its input from a queue instead of from HTTP: the same CPU slots, concurrency limit and memory budget, and it needs a database exactly the way a server does. A `worker` kind would have duplicated `ServerSettings`, `ServerModel` and `resolveServerBranch` wholesale — the same one-thing-two-names problem removed in entry 043. So there is one new component, `queue`, and its consumer is an ordinary Application Server that the user renames. A test asserts the worker can use a database of its own, because that inheritance is the entire justification.

**A job is a request that starts somewhere else.** The first design had a separate `JobState` travelling its own path through the engine, which meant a second branch in every handler. Instead a queue compiles to a **consumer route**: the same pipeline — admission, CPU segments, cache, database — entered from the queue instead of from a client, and finished instead of answered. The queue-to-worker link carries the message in its forward direction and the acknowledgement back in its reverse, which is a hop a real consumer pays anyway. Two small changes to `completeRequest` were the whole of it.

**Pull, where everything else pushes.** Every other flow is push: a station finishes and hands the request on. A queue is the opposite — work sits still until a consumer comes for it, which is exactly why a backlog can grow. `dispatchFromQueue` runs on the two events that change either side: a message arriving, and a consumer finishing one. It is bounded by `inFlight`, not only by `canAdmitNow`, because a message spends a moment on the link before the server has admitted it and without that bound the consumer takes more than it can hold.

**A full queue refuses the publish.** The alternative — accept and drop — would hide the failure. Refusing makes the request fail with `queue-full`, so backpressure appears in the rejection figures instead of vanishing.

**A fourth kind of charge.** A managed queue has nothing to provision: the entire bill is what passed through it, and none of `compute`, `storage` or `egress` says that. `ChargeType` gained `requests`, priced per million and projected from the *measured* rate exactly as egress is (ADR-007), never from the run's own total. Illustrative profiles for SQS and Pub/Sub carry `verified: false`, a real source URL and a note saying nothing was verified; a self-managed broker profile has no amount at all, so it reports **unpriced** rather than zero.

**Two things the arrival work needed.** Poisson draws from a stream of its own (`arrival:<clientId>`), so adding it cannot shift what any cache draws — a test pins that by running the same design with `constant` and with a ramp whose mean multiplier is 1. And shaped multipliers stop at 0.01 rather than 0, because a rate of exactly zero means an infinite wait for the next request, which would end that client's traffic for the rest of the run instead of merely making it slow.

**Closed-loop clients report two rates, not one.** In closed mode there is no configured rate to report, so `offeredRatePerSecond` became the *ceiling* — what the users would offer if every answer were instant — and `achievedRatePerSecond` was added for what actually happened. One meaning each, rather than one field meaning two things.

**Two pre-existing bugs found on the way.** `run-schema.ts` lists every value it will accept, and it had not been updated since the load-balancer work: `clients` was not listed at all, the balancer was missing from the station kinds, and `balancer-queue-full` was missing from the rejection reasons. The effect was worse than dropped fields — **importing a project that used a load balancer rejected its entire run history**. A test reproduces it: removing the fix makes the import return the run as skipped. It also explains the defensive `?? []` reads added when `result.clients is not iterable` appeared earlier. New and possibly-absent fields are now `.default()`ed so older exports still load.

**Verification:** `npx tsc --noEmit` passes; `npx vitest run` — 126 passed (36 new across arrivals, queues, pricing, persistence); `npx playwright test` — 24 passed (2 new); `npm run build` succeeds. Hand-checked figures: a worker at 200 ms drains 5 a second, so 110 seconds of run leaves 550 of 1,000 messages done and 450 waiting, and the test asserts that band; 1,000 messages in 10 measured seconds projects to 262.8 million a month, priced at the illustrative 0.40 per million as exactly `105.12`. In the browser, the new template published 1,334 messages, processed 734, left **600 outstanding** with a peak depth of 844 — while the average response stayed at 41.19 ms and nothing was rejected, which is the whole argument for a queue in one line of numbers.

- **Request:** "Let's add these components: 1. DNS 2. CDN 3. API Gateway 4. WAF/Reverse Proxy."
- **Files changed:** `src/domain/types.ts`, `src/domain/defaults.ts`, `src/domain/schema.ts`, `src/catalogs/types.ts`, `src/simulation/routing.ts`, `src/simulation/engine.ts`, `src/simulation/types.ts`, `src/simulation/models/station.ts`, `src/simulation/models/link.ts`, `src/pricing/pricing.ts`, `src/storage/run-schema.ts`, `src/ui/icons.tsx`, `src/app/styles.css`, `tailwind.config.js`, `src/features/editor/{Palette,Canvas,Inspector}.tsx`, `src/features/results/{node-metrics.ts,ResultsPanel.tsx}`, `scripts/refresh-cloud-prices.mjs`, `public/catalogs/cloud-profiles.v1.json` (regenerated), `tests/helpers.ts`, `README.md`, `architecture.md`, `techniques.md`, `future.md`, `acceptance-audit.md`. **Created:** `tests/edge.test.ts`, `e2e/edge.spec.ts`.
- **What each one is, in one line each.** DNS turns a name into an address before the request is sent. A CDN is a cache at the edge: a hit is answered there and never reaches the origin. A WAF inspects every request and turns a share away. An API gateway is the front door, and the one component that says no on purpose: above its rate limit, requests are refused rather than queued. None of the four computes; none is a server.
- **Three are hops, one is beside the path.** The CDN, WAF and gateway are service stations chained in front of the entry point, in any order and any number, each forwarding to exactly one thing. The routing walk stops at the first thing that is not an edge kind, so every existing entry-point rule applies unchanged behind them; a hop that forwards to nothing, to two things, or back into the chain has its own error. DNS is different: a request does not go *through* it. A configured share of requests — 2% by default, standing in for users without a cached answer — ask it first, wait, then set off. Making DNS a hop would have charged every request a lookup, wrong by a factor of fifty.
- **One reason each to stop a request.** The CDN samples a hit from its rate and sends the response straight back along the chain. The WAF samples a block and rejects as `waf-blocked`. The gateway keeps a token bucket — refilled at the limit, capped at the burst allowance — and rejects `gateway-throttled` on the spot; its own queue never grows from throttling, which a browser test asserts. Each hop draws from its own stream, so a zero-rate WAF leaves the CDN's draws untouched, and a test pins that too.
- **Responses retrace the chain.** A route records `relayBack`, the reverse link for every link on the way in, so a response from the balancer goes back through the gateway, the WAF and the CDN to the users. A consequence worth knowing: bytes to users now leave the CDN, so the CDN carries the egress charge and the balancer's egress falls to nothing when a CDN is in front.
- **What the shares are.** The hit rate, the block rate and the lookup share model nothing about the traffic — nothing here knows what is being asked for or what a firewall would flag. They are assumptions, sampled from the run seed like the cache's hit rate, and every form says so. What the simulation shows is the *consequence*: with the default CDN, everything behind it sees a fifth of the load, and two servers carry what four did.
- **Real prices for all four.** The refresh script now reads Route 53 ($0.40 per million queries), CloudFront ($1.00 per million HTTPS requests, $0.085 per GB to users), API Gateway HTTP API ($1.00 per million) and AWS WAF ($5.00 per web ACL per month, spread hourly, plus $0.60 per million requests) from the AWS bulk price lists — Route 53 and CloudFront from the global file, since they are not priced per region — and Azure DNS and Azure CDN from the Retail Prices API. Fixed charges the pricing engine has no line for — hosted zones, WAF rules — are named in each profile's note as not modelled. The catalog has 34 profiles, 20 verified; four self-managed unpriced profiles cover running these yourself.
